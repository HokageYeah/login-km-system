# 通用卡密与授权系统智能体配置工作区 (KM Workspace Rules)

这份文档是专门写给你（AI 智能体 / 编程助手）的当前项目全局上下文与强制开发规范。在处理本项目任何任务前，请自动读取并遵循本文件中的约定。

## 0. AI 通用编码与行为准则

**权衡：** 这些指南偏向谨慎而非速度。对于琐碎任务，请自行判断。

### 0.1 先思考再编码
**不要假设。不要隐藏困惑。暴露权衡。**
在实现之前：
- 明确陈述你的假设。如果不确定，请提问。
- 如果存在多种解释，请列出来——不要默默选择一种。
- 如果有更简单的方法，请说出来。在合理时提出反对意见。
- 如果有不清楚的地方，停下来。指出困惑之处。提问。

### 0.2 简单至上
**解决所需问题的最少代码。不做推测性工作。**
- 不要超出要求范围的功能。
- 不要为一次性使用的代码创建抽象。
- 不要添加未经要求的"灵活性"或"可配置性"。
- 不要为不可能发生的场景编写错误处理。
- 如果你写了 200 行代码而本可以只写 50 行，请重写。
- 问自己："资深工程师会觉得这过度复杂了吗？" 如果是，就简化。

### 0.3 手术式修改
**只触及你必须改的地方。只清理你自己造成的混乱。**
在编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的东西。
- 匹配现有风格，即使你个人会有不同做法。
- 如果你注意到不相关的死代码，可以提一下——但不要删除它。
当你的修改产生了孤立代码：
- 删除因**你的修改**而变得未使用的导入/变量/函数。
- 除非被要求，否则不要删除预先存在的死代码。
- **检验标准**：每一行修改都应该直接追溯到用户的需求。

### 0.4 目标驱动执行
**定义成功标准。循环执行直到验证通过。**
将任务转化为可验证的目标：
- "添加校验" → "为无效输入编写测试，然后让测试通过"
- "修复这个 bug" → "编写一个能复现它的测试，然后让测试通过"
- "重构 X" → "确保重构前后测试都能通过"
对于多步骤任务，陈述一个简要计划：
1. [步骤] → 验证: [检查点]
2. [步骤] → 验证: [检查点]
3. [步骤] → 验证: [检查点]

## 1. 项目特定指南

- **项目定义**：这是一个以 **服务端为最终授权裁决中心** 的通用卡密与授权系统，面向多个桌面程序或应用提供统一的用户认证、卡密绑定、设备控制、权限校验、后台管理能力。
- **当前状态**：根据项目文档与当前代码，系统的核心阶段已经开发完成，当前工作重点不再是“从零搭框架”，而是 **沿着既有架构继续做规范化开发、功能补强、稳定性修复与可维护性优化**。
- **当前仓库重心**：本仓库当前主要是 **FastAPI 后端工程**。文档中提到的客户端 / 管理后台能力是系统业务范围的一部分，但当前代码主干以后端 API、服务层、数据库模型、测试与文档为核心。
- **核心业务能力**：
  - 用户注册 / 登录 / JWT 鉴权
  - 多应用管理
  - 卡密生成 / 绑定 / 查询 / 设备解绑
  - 基于卡密的功能权限校验
  - 管理员后台能力（用户、卡密、设备、应用、权限）
  - 功能权限元数据管理（`feature_permissions`）

## 3. 核心技术栈与真实工程约束

- **后端框架**：FastAPI
- **ORM / 数据库**：SQLAlchemy + Alembic + MySQL
- **配置管理**：`python-dotenv` + `pydantic-settings`
- **鉴权**：JWT（`python-jose`）+ `passlib[bcrypt]`
- **日志**：`loguru` + `colorama`
- **测试**：`pytest` + `pytest-asyncio` + `pytest-cov`

### 3.1 依赖管理规则

- 当前项目 **不是 Poetry 项目**，以根目录的 `requirements.txt` 为依赖基准。
- 如需新增依赖，必须：
  - 明确说明新增原因；
  - 保持依赖克制，避免无必要引入大包；
  - 同步更新 `requirements.txt`；
  - 同步考虑测试环境是否可运行。
- 不要照搬其他项目的 Poetry 规则到本仓库。

### 3.2 配置与环境规则

- 环境配置文件位于根目录：
  - `.env`
  - `.env.development`
  - `.env.production`
  - `.env.test`
- 数据库结构变更以 **Alembic 迁移** 为正式交付方式，不要只改模型而不补迁移。
- 配置入口：`app/core/config.py`
- 数据库连接配置：`app/config/database_config.py`
- 数据库连接与会话工厂：`app/db/sqlalchemy_db.py`

## 4. 真实代码架构与职责分层

### 4.1 主入口与路由入口

- 应用入口：`app/main.py`
- 路由聚合：`app/api/api.py`
- API 前缀：`/api/v1`

### 4.2 核心分层

- `app/api/endpoints/`
  - 负责路由、参数接收、依赖注入、响应模型转换
  - 不要把大段业务规则直接堆在接口层
- `app/services/`
  - 负责核心业务逻辑
  - 这是用户登录、卡密绑定、权限校验、后台管理的主要实现层
- `app/models/`
  - 负责数据库模型、关系映射、状态枚举
- `app/schemas/`
  - 负责 Pydantic 请求 / 响应模型
- `app/utils/`
  - 放置安全工具、卡密生成器、依赖函数等公共能力
- `app/middleware/`
  - 负责统一异常处理、统一响应格式处理
- `tests/`
  - 当前测试主干集中在认证、卡密、权限三个核心链路
- `app/docs/`
  - 项目任务、设计、阶段报告、接口说明、使用手册的主要沉淀位置

### 4.3 当前核心路由模块

- `auth.py`：注册、登录、校验 Token、当前用户信息
- `card.py`：我的卡密、绑定卡密、解绑设备、卡密详情
- `app.py`：应用创建、列表、启用禁用、公开应用列表
- `permission.py`：单个权限校验、批量权限校验、查询我的权限
- `admin.py`：用户 / 卡密 / 设备 / 统计等后台能力
- `feature_permission.py`：功能权限元数据管理、卡密功能权限配置

### 4.4 历史或旁路模块的处理原则

以下模块不是当前卡密授权主链中心，除非任务明确要求，否则不要围绕它们扩展主业务：

- `app/api/endpoints/wx_public.py`
- `app/api/endpoints/test_api.py`
- `app/services/wx_public.py`
- `app/models/article.py`

如果某次需求确实涉及这些模块，也必须先判断它是否应该独立维护，还是应该抽象成主链的公共能力。

## 5. 核心业务设计与不可破坏的稳定边界

### 5.1 服务端裁决原则

- 客户端只负责：
  - 登录 / 注册
  - 展示界面
  - 在执行功能前调用服务端权限校验
- **所有最终授权判断都必须在服务端完成**。
- 不要把“是否允许使用某功能”的核心判定下放到客户端本地逻辑。

### 5.2 关键业务主链

#### 1. 登录链路

- 校验 `app_key` 是否存在且可用
- 校验用户名、密码、用户状态
- 生成 JWT
- 将 token 持久化到 `user_tokens`
- token 维度至少包含：
  - `user_id`
  - `app_id`
  - `device_id`
  - `role`

#### 2. 卡密绑定链路

- 校验卡密存在
- 校验卡密属于当前应用
- 校验卡密状态不是禁用
- 校验卡密未过期
- 校验用户绑定关系
- 校验设备绑定关系
- 校验设备数量不超过 `max_device_count`
- 创建 / 更新 `user_cards`、`card_devices`
- 首次使用时更新卡密状态为 `used`

#### 3. 权限校验链路

当前权限校验是系统核心稳定边界，扩展时不要破坏：

1. 校验用户存在且未封禁
2. 查询用户有效卡密绑定
3. 过滤禁用卡密 / 过期卡密
4. 校验设备是否已绑定到该卡密
5. 校验设备状态是否可用
6. 校验权限配置是否匹配
7. 更新设备最后活跃时间

#### 4. 后台即时生效原则

- 管理员修改用户状态、卡密状态、设备状态、卡密权限后，应尽量保持 **即时生效**。
- 新功能不要引入“必须重登才能生效”的额外耦合，除非这是经过明确设计的安全机制。

### 5.3 数据模型边界

当前核心数据实体应围绕以下模型理解和扩展：

- `apps`
- `users`
- `cards`
- `user_cards`
- `card_devices`
- `user_tokens`
- `feature_permissions`（扩展权限元数据表）

特别说明：

- 较早文档多以“6张核心表”描述系统，但 **当前代码已经正式引入 `feature_permissions` 作为权限元数据扩展表**。
- 后续涉及权限中心化、权限列表管理、卡密权限配置标准化的需求时，应把它视为正式能力，而不是临时脚手架。

如果新增数据库结构，先判断：

- 这是核心主链必需的稳定扩展吗？
- 是否可以通过补强现有表结构或现有服务完成？
- 是否会破坏当前多应用、多设备、权限实时校验的设计？

### 5.4 权限配置兼容性规则

当前系统已经支持多种权限配置格式，后续开发必须保持兼容：

- `list[str]`
- `dict[str, bool]`
- JSON 字符串（服务层会尝试解析）

规范要求：

- **新增能力优先使用 `permission_key` 列表格式**，便于与 `feature_permissions` 对齐。
- **任何新实现都不能轻易破坏现有 list / dict / JSON string 的兼容性**。
- 不要把某个权限写死在零散 if 分支里；优先让权限成为可配置、可查询、可管理的数据。

### 5.5 响应格式边界

- 当前 API 统一响应边界围绕 `app/schemas/common_data.py` 中的 `ApiResponseData`。
- `app/middleware/response_validator.py` 和 `app/middleware/exception_handlers.py` 会参与响应包装与异常格式统一。
- 扩展接口时：
  - 优先复用现有响应模型与统一格式；
  - 不要引入新的、与现有主链完全无关的返回协议；
  - 不要破坏 `platform / api / data / ret / v` 这类统一结构边界。

## 6. 开发纪律与强制规范（必须严格遵守）

### 6.1 中文注释、中文日志、解释“为什么”

- 所有新增代码注释、开发说明、接口文档、对项目的解释，统一使用 **简体中文**。
- 关键业务步骤必须补充 **中文日志**，尤其是：
  - 登录失败原因
  - 卡密绑定失败原因
  - 权限校验命中 / 拒绝原因
  - 管理员关键操作
  - 数据库事务回滚与异常
- 注释不要只写“做了什么”，尽量解释：
  - 为什么这样设计
  - 为什么不能写成更简单但错误的方式
  - 为什么这里要兼容旧格式 / 历史行为

### 6.2 优先做通用修复，禁止单点打补丁

- 修问题前先判断根因所在层级：
  - 接口层
  - Schema 层
  - Service 层
  - Model / DB 层
  - 鉴权依赖层
  - 中间件 / 异常处理 / 响应包装层
- 如果某问题有较高概率会在：
  - 其他接口
  - 其他权限
  - 其他应用
  - 其他设备
  - 其他卡密
  - 其他管理员操作
  中重复出现，就必须优先做 **公共层修复**，而不是针对当前一个接口写死分支。

禁止：

- 只对某个用户名、某个 `app_key`、某个 `permission_key` 硬编码兜底
- 只对某条错误文案做脆弱字符串匹配修复
- 在 endpoint 内复制一套 service 逻辑
- 用更多临时判断掩盖主链设计问题

### 6.3 禁止过度设计：最简、最稳、最容易维护

- **禁止过度设计**。不要为了“看起来更完整”“以后也许会用到”“抽象上更优雅”而提前引入并不必要的层、配置、状态、流程或框架。
- 优先补强现有机制，不要轻易平行再造一套新机制。
- 能在现有 `service + schema + endpoint + middleware` 结构中解决的，不要额外引入复杂编排。
- 不要为了“未来可能会用”就提前堆过多抽象、过多配置、过多状态字段。
- 所谓“最优”，是用 **最少必要复杂度覆盖最多真实场景**。

开发前必须先自检：

- 这个问题是否真的需要新增一层抽象，而不是补强现有公共层？
- 这个配置项、状态字段、兜底逻辑，是否已经有明确且稳定的复用场景？
- 这个设计是否会增加理解成本、调试成本、测试成本、维护成本？
- 如果现在不做这层抽象，是否仍然能稳定、清晰地完成当前需求？

明确禁止以下过度设计行为：

- 为单个需求同时引入多套重叠机制
- 为低概率场景提前铺设完整框架
- 用大量可配置化替代一个本可稳定抽象的公共规则
- 用多层隐式回退、魔法逻辑、超长兜底链掩盖主链问题
- 在还没有真实复用需求时，提前拆分过细模块或定义过多中间层

### 6.4 保持分层清晰

- Endpoint 负责请求与响应，不负责大段业务编排。
- Service 负责业务规则，不负责 HTTP 层细节。
- Model 负责表结构与关系，不负责接口协议。
- Schema 负责校验和返回，不要承载数据库操作。
- Middleware / Exception Handler 负责统一协议与全局拦截，不要把业务规则塞进去。

### 6.5 数据库改动必须完整闭环

只要涉及表结构、字段、索引、约束变化，至少要同步考虑：

- `app/models/` 模型定义
- Alembic 迁移
- 初始化脚本 / 测试数据脚本是否需要调整
- 受影响的 `schemas`
- 受影响的 `services`
- 受影响的 `endpoints`
- 相关文档
- 相关测试

禁止只修改模型或 `create_all()` 相关逻辑，而不补正式迁移与文档说明。

### 6.6 测试环境兼容性

- 当前测试主要使用 **SQLite 内存数据库**。
- 新增数据访问逻辑时，要尽量兼顾：
  - MySQL 真实运行环境
  - SQLite 测试环境
- 尽量避免无必要的数据库方言特性或仅 MySQL 才能跑通的写法；若必须使用，要明确说明并补测试方案。

### 6.7 前端边界说明

- 当前仓库没有成熟的独立前端工程目录可作为主要开发对象。
- 未经用户明确要求，不要臆造一个新的 `web/` 前端体系并把工作重心迁移过去。
- 如果任务涉及前端页面、管理后台界面、落地页、组件视觉、交互优化、UI 评审等工作，**前端 UI 设计可以使用技能 `.agent/skills/ui-ux-pro-max` 作为首选设计参考与执行能力**。
- 使用 `ui-ux-pro-max` 时，优先吸收其在视觉风格、配色、字体搭配、布局、动效、可访问性、栈最佳实践上的指导，而不是只照搬表面样式。
- 如果项目后续已经形成明确的前端技术栈或设计系统，必须优先兼容现有栈与现有视觉语言，不要为了套用技能强行换栈、重置风格或推翻现有界面体系。
- 如果任务需要补管理后台页面或客户端协作说明，应优先：
  - 先补后端接口与文档；
  - 再基于用户明确要求设计前端交互层。

## 7. 标准开发顺序（后续新增 / 修改功能时照此执行）

### 7.1 通用执行顺序

1. 先读任务文档、设计文档、README、相关实现文件
2. 找到真正受影响的稳定边界与抽象层
3. 优先修改 Service 层与公共层，再回填 Endpoint / Schema
4. 如涉及数据库变更，同步补模型与迁移
5. 补中文日志、注释、异常信息
6. 补相关测试
7. 更新相关文档

### 7.2 按改动类型的优先落点

#### 认证相关改动
优先关注：
- `app/services/auth_service.py`
- `app/utils/security.py`
- `app/utils/dependencies.py`
- `app/api/endpoints/auth.py`

## 8. 测试与验收要求

### 8.1 最低测试要求

发生改动后，至少运行与改动相关的测试文件。当前主测试文件：

- `tests/test_auth.py`
- `tests/test_card.py`
- `tests/test_permission.py`

### 8.2 需要扩大验证范围的情况

如果改动涉及以下任一情况，不能只跑单个小测试：

- Token 认证链路
- 卡密绑定逻辑
- 权限校验逻辑
- 公共依赖注入
- 统一异常处理
- 统一响应包装
- 数据模型或数据库结构

此时应至少覆盖多个相邻链路，避免改一处坏一片。

### 8.3 测试之外的自检要求

除了自动化测试，还要自检：

- Swagger 接口是否仍可理解
- 响应格式是否仍符合统一规范
- 错误提示是否是中文且可排查
- 管理员改动是否即时生效
- 是否破坏多应用 / 多设备 / 权限实时校验的主设计

## 10. 你在本项目中的工作目标

你不是来“另起炉灶重做一个系统”的，而是要在 **当前卡密授权系统既有设计上继续稳定迭代**。你的目标始终是：
