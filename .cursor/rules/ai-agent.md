# AI Agent 项目智能体配置工作区 (AI Workspace Rules)

这份文档是专门为你（AI 智能体/编程层助手）整理的当前项目全局上下文与严格开发规范。在处理当前项目的任何任务前，请自动读取并遵循本文件的所有约定。

## 1. 项目状态与概览
- **项目定义**：一个高度模块化、基于 FastAPI 和 LangGraph 的全流程 AI Agent 智能体框架。
- **当前进度**：系统核心阶段设计中的 **阶段零、一、二、三、四、五、六 的任务均已开发完成，并全部通过了对应的测试用例**。
- **核心组件**：涵盖统一 LLM 调用适配、自有 Tool库 / Skill库、由状态图驱动的 Agent 引擎（包含 Planning/Execution/Reflection 和容错模块），以及面向渠道的 REST API 与 Vue3 前端管理界。
- **参考架构**：系统实现了完整的 [基于工具白名单过滤与自分析的 LLM 自我纠错与反思机制]。

## 2. 核心技术栈
- **后端**：Python 3.13 + FastAPI + LangGraph + SQLAlchemy + Alembic
- **前端**：Vue 3 (Composition API) + TypeScript + Vite + Element Plus (`web/` 目录)

## 3. 开发纪律与强制规范（🔴 必须严格遵守）

### 3.0 核心文档阅读与边界约束（防跑偏指南）
- **核心文档**：在规划和着手任何特定任务之前，**请仔细阅读项目设计文档 (`docs/ai-agent-simple-desigin.md`)，以及任务文档 (`docs/ai-agent-simple-task.md`) 的要求**。
- **架构流程图**：请务必在开始重大设计之前，先阅读项目架构流程图 (`docs/ai-agent-simple-desigin.md`)内的架构流程图部分，了解项目整体结构与架构逻辑。
- **全景架构与运行时序**：在开始重大设计之前，请务必读取 **`README.md`** 文档，了解项目的全局目录结构、核心全景架构图以及 Agent 调用和 SSE 流式的时序说明等必要信息。
- **防止跑偏**：务必了解项目整体结构与架构逻辑。让 AI **每次执行的时候不要设计跑偏**，严格遵守既有项目的架构思路和任务边界。

### 3.1 依赖管理限制
- 后端项目由 **Poetry** 接管。`pyproject.toml` 和 `poetry.lock` 是唯一合法的依赖配置文件。
- **严禁** 直接使用 `pip install` 安装新的第三方库，必须使用 `poetry add <package>`，并确保在 poetry 虚拟环境中运行。

### 3.2 中文日志与详尽注释（易读性要求）
- 所有的代码注释、文档与交流必须使用 **简体中文**。
- **打印日志要求**：请要求开发代码的时候要**尽量多地创建中文打印日志**（后端必须结合自带的 `loguru` 和 `colorama` 区分颜色和层级），实时打印出 Agent 的思维流、执行细则和流转卡点，方便后续查看、更改、调试、理解意思使用。
- **详细注释**：代码切忌只写功能描述，重点增加“**为什么这样做**”的设计解释，以及相关的**代码详细注释**。无论是后端 Python 还是前端 TypeScript 都必须保持这一严谨标准，为后续查看和更改提供依据。

### 3.3 前端设计风格约定
- 前端页面 (`web/` 下的 Vue.js 代码) 的设计生成必须使用技能包中的 **`ui-ux-pro-max`** 技能设计规范。
- 确保页面美学保持统一（毛玻璃、渐变、扁平化与现代间距布局），避免生成老旧的 Bootstrap 默认风格界面。
- 前端同样需增加关键执行步骤的 `console.log` 以及大量核心代码中文注释。

### 3.4 通用性与全局设计原则（禁止单点打补丁）
- 无论是 **修复问题、优化代码、实现新需求、补齐兼容性、调整提示词、改造流程**，都**禁止只围绕当前单一案例做临时补丁式修改**；必须先判断问题究竟属于：
  - 某个单文件局部问题；
  - 某类能力的共性问题；
  - 某条主链路的架构问题；
  - 某个抽象层（Tool / Skill / Agent / Memory / Prompt / Gateway / 路由 / 解析器 / 状态流）的通用缺陷。
- 在动手修改前，必须优先思考 **“这是不是一个会在其他技能、其他工具、其他 Agent、其他模型输出、其他渠道、其他任务中重复出现的问题”**。如果答案有较大概率是“会”，则必须优先做 **通用性修复**，而不是只为当前样例硬编码。
- **禁止为单一技能、单一日志、单一提示词、单一测试样例写死特殊分支**，除非已经有充分证据证明它确实是不可复用的特例；若确属特例，也必须在注释中明确说明“为什么只能特殊处理、为什么不能抽象到公共层”。
- 修复问题时，优先改造以下**公共层与稳定边界**，而不是把逻辑散落在调用点上：
  - 公共解析器；
  - 公共错误处理与重试机制；
  - 公共依赖检查与安装机制；
  - 公共路由、授权、兼容层；
  - 公共 Prompt 约束、记忆注入、状态传递；
  - 公共模型与元数据结构。
- 任何兼容性修改，都必须同时考虑：
  - **本地创建的标准能力包**；
  - **外部下载的非标准能力包**；
  - **历史旧数据 / 旧配置 / 旧流程**；
  - **未来新增能力的可扩展性**。
- 设计与编码时，默认遵循 **“优先增强框架通用能力，而不是修死单个业务点”** 的原则。若当前案例暴露的是框架短板，应直接补框架，不要把责任推回给单个技能或调用方。
- 当需要做兜底逻辑时，优先选择 **可复用、可组合、可观测、可测试** 的方案，避免出现：
  - 只对某个字符串生效；
  - 只对某个 skill_id 生效；
  - 只对某条日志文案生效；
  - 只对某个模型供应商输出格式生效；
  - 只在当前手工复现场景下生效。
- 在满足正确性、通用性、可扩展性和兼容性的前提下，必须同时遵循 **“最简、最优设计原则，禁止过度设计”**：
  - 优先选择 **结构更简单、依赖更少、状态更少、链路更短、概念更少** 的实现方案，避免为了“可能未来会用到”而提前引入额外抽象层、额外配置项、额外状态字段、额外提示词分支或额外路由规则。
  - 新增任何抽象、配置、状态、兜底机制前，必须先自问：
    - 现有公共层是否已经能承载这项需求，只是缺少一处补强？
    - 是否可以通过复用既有注册表、既有状态流、既有上下文注入、既有校验机制来解决，而不是再造一层？
    - 是否存在至少一个明确的相邻复用场景，而不是只因为“以后也许有用”就先设计进去？
  - 若一个问题可以通过 **补强现有公共机制** 解决，就不要再新增并行机制；若可以通过 **增加约束** 解决，就不要升级为复杂编排；若可以通过 **少量稳定元数据** 解决，就不要引入大而全的配置体系。
  - 设计评估时必须同时比较“实现成本 / 理解成本 / 调试成本 / 测试成本 / 后续维护成本”，不能只看抽象上是否“更完整”；如果一个方案理论上更通用，但明显增加系统复杂度且当前没有稳定复用收益，应优先采用更克制的方案。
  - 所谓“最优”不是堆能力最多，而是 **在正确解决问题的前提下，用最少必要复杂度覆盖最多真实场景**；必须警惕：
    - 为一个问题同时引入多套相互重叠的机制；
    - 为了少数低概率场景提前铺设完整框架；
    - 用大规模可配置化替代一个本可稳定抽象的公共规则；
    - 用多层回退、隐式魔法和过量兜底掩盖本该直接修复的主链路问题。
- 开发过程中应主动进行“相邻场景外推”，至少自检以下问题：
  - 这个修复是否只覆盖当前输入，换一种等价输入就失效？
  - 这个修复是否只覆盖当前技能，换成其他技能/工具也应成立吗？
  - 这个修复是否破坏现有标准链路、旧版本兼容性或通用抽象？
  - 这个修复是否应该沉淀为公共工具函数、公共组件、公共约束或公共测试？
- 在提交实现时，若改动涉及通用链路，必须同步补充：
  - **通用规则层面的注释或文档**；
  - **覆盖当前场景 + 至少一个相邻场景的测试**；
  - **必要的中文日志与错误信息**，确保后续排查时能看出这是“框架级处理”还是“业务级处理”。
- 若发现需求表面上是一个点状问题，但根因实际是全局架构缺陷，应明确按照 **“先定位根因层级，再在正确抽象层修复”** 的方式开发，避免继续堆积技术债。

## 4. 测试执行保障
在变动核心功能后，必须验证没有破坏已有进度。当前主要依赖的集成测试文件包括：
- 阶段 0~5 的测试：`tests/integration/test_end_to_end_phase0_to_5.py`
- 全阶段(含流程端到端执行)：`tests/integration/test_end_to_end_phase0_to_6.py`
项目下: `tests/` 目录下有所有阶段的测试文件。

*遇到需求不明朗时，请随时提问；确认修改步骤后即可着手修改。*
