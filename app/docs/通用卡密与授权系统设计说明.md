# 通用卡密与授权系统设计说明

> 目标：
>
> * 一套 **可复用的卡密 / 授权平台**，支持多个桌面程序或应用
> * 支持：用户控制、卡密控制、设备控制、权限控制、封禁、实时改权限
> * 第一版：不过度复杂，但具备商业可用性

---

## 一、整体架构

```
┌────────────────────────┐
│   授权 / 卡密中心（服务端） │
│                        │
│ - 用户系统              │
│ - 应用管理              │
│ - 卡密管理              │
│ - 设备管理              │
│ - 权限校验              │
│ - 封禁 / 改权限          │
└─────────▲──────────────┘
          │ HTTPS
┌─────────┴──────────────┐
│   桌面程序 / 客户端     │
│  Python + Vue3 + EXE    │
└────────────────────────┘
```

客户端只负责：

* 登录 / 注册
* 展示 UI
* 每次功能前向服务端请求权限校验

**所有是否可用的最终判定，都在服务端。**

---

## 二、核心业务流程

### 1. 用户流程

1. 启动客户端
2. 登录 / 注册（用户名 + 密码）
3. 登录成功 → 查询是否已绑定卡密
4. 若无卡密 → 强制停留在【卡密绑定页】
5. 若有卡密 → 获取权限、过期时间、设备信息

### 2. 功能使用流程（强制）

```
点击功能
  ↓
检查是否登录
  ↓
检查是否绑定卡密
  ↓
向服务端校验权限
  ↓
允许 / 拒绝执行
```

## 三、数据库设计

### 1️⃣ 应用表（app）

```sql
app
- id
- app_key            -- 应用唯一标识（内置在客户端）
- app_name
- status             -- normal / disabled
- created_at
```

---

### 2️⃣ 用户表（user）

```sql
user
- id
- username
- password_hash
- status             -- normal / banned
- created_at
- last_login_at
```

> 封禁用户 = 所有应用不可用

---

### 3️⃣ 卡密表（card）

```sql
card
- id
- app_id                     -- 所属应用
- card_key                   -- 卡密字符串（唯一）
- status                     -- unused / used / disabled
- expire_time                -- 过期时间
- max_device_count           -- 最大可绑定设备数
- permissions                -- JSON 权限
- remark                     -- 套餐/备注
- created_at
```

#### permissions 示例

```json
{
  "wechat": true,
  "ximalaya": false
}
```

或：

```json
["wechat", "ximalaya"]
```

---

### 4️⃣ 用户-卡密绑定表（user_card）

```sql
user_card
- id
- user_id
- card_id
- bind_time
- status              -- active / unbind
```

> 支持：一个用户绑定多个卡密（后期扩展）

---

### 5️⃣ 卡密-设备绑定表（card_device）

```sql
card_device
- id
- card_id
- device_id
- device_name         -- 可选（PC 名称）
- bind_time
- last_active_at
- status              -- active / disabled
```

绑定时规则：

```
已绑定设备数 < max_device_count
```

---

### 6️⃣ 用户 Token 表（可选）

```sql
user_token
- id
- user_id
- app_id
- token
- device_id
- expire_time
```

> 用于：踢下线、强制失效、设备级登录控制

---

### 7️⃣ 功能权限元数据表（feature_permission）

```sql
feature_permission
- id
- permission_key          -- 权限唯一标识
- permission_name         -- 权限显示名称
- app_id                  -- 所属应用ID
- description             -- 权限描述
- category                -- 历史兼容分类字段
- icon                    -- 前端展示图标
- sort_order              -- 排序
- status                  -- normal / disabled
- created_at
- updated_at
```

设计说明：

- `cards.permissions` 负责“某张卡拥有哪些权限”；
- `feature_permissions` 负责“系统里有哪些可配置权限，以及这些权限怎么展示”；
- 两者通过 `permission_key` 解耦关联，这样管理后台、权限校验、跨服务器迁移都能复用同一套权限标识。
- `app_id` 是权限的正式归属字段，管理后台中的“权限分类”统一解释为“所属应用”；
- 不额外引入权限-应用关联表，因为当前业务约束是“一条权限只属于一个应用”，直接外键最简单、最稳定、最容易维护；
- `category` 保留为历史兼容字段，主要用于兼容旧导入文件、旧页面展示和老数据迁移，不再作为新的主分类依据。

#### 权限归属应用设计原则

```text
一个权限  ->  只属于一个应用
一个应用  ->  可以拥有多个权限
```

为什么这样设计：

1. 权限在后台管理时需要稳定分组，应用维度比自由输入分类更可靠
2. 卡密本身已经绑定 `app_id`，因此卡密可选择的权限天然应受所属应用约束
3. 导入导出需要跨服务器迁移时，应用信息必须成为结构化数据，不能只依赖自由文本分类
4. 如果未来真的出现“同一权限需要复用到多个应用”的场景，再升级为多对多关联表更合理；当前阶段不应过度设计

#### 管理后台权限管理设计补充

围绕“权限归属应用”这次改造，后台管理遵循以下通用规则：

1. 功能权限列表按应用维度管理，而不是继续沿用手工输入分类做主入口
2. 卡密管理页与权限管理页中的“所属应用”都使用统一颜色规则，颜色由应用标识稳定映射得到
3. 应用管理页不再只展示静态应用信息，而是承担应用维度导航入口：
   - 展示当前应用下的卡密数量
   - 展示当前应用下的权限数量
   - 点击统计值直接跳到对应列表页，并自动携带应用筛选条件
4. 功能权限支持批量删除，但删除的是权限元数据，不自动修改历史卡密的 `permissions` 内容

这样设计的原因：

- 应用是卡密、权限、登录裁决三条主链共同依赖的核心实体，后台也应围绕应用组织管理入口；
- 颜色映射属于纯展示层问题，应由前端统一算法解决，而不是额外增加数据库字段或配置表；
- 应用统计属于列表通用信息，应由后端聚合一次性返回，避免前端为每行数据再发请求形成 N+1；
- 权限删除不联动改写历史卡密，是为了避免“删展示元数据时误伤历史授权记录”。

## 四、接口设计

### 1️⃣ 登录 / 注册

```http
POST /api/auth/register
POST /api/auth/login
```

登录成功返回：

```json
{
  "token": "jwt_token",
  "user_status": "normal"
}
```

---

### 2️⃣ 查询用户卡密状态

```http
GET /api/card/my
Authorization: Bearer token
```

返回：

```json
{
  "has_card": true,
  "cards": [
    {
      "card_key": "****-****",
      "expire_time": "2026-01-01",
      "permissions": ["wechat"],
      "bind_devices": 1,
      "max_device_count": 2
    }
  ]
}
```

---

### 3️⃣ 绑定卡密

```http
POST /api/card/bind
Authorization: Bearer token
{
  "card_key": "XXXX-XXXX",
  "device_id": "abc123",
  "device_name": "MyPC"
}
```

校验逻辑：

1. 卡密是否存在
2. 是否属于当前应用
3. 是否禁用 / 是否过期
4. 是否超过最大设备数

---

### 4️⃣ 功能权限校验（每个功能必调）

```http
POST /api/permission/check
Authorization: Bearer token
{
  "permission": "wechat",
  "device_id": "abc123",
  "card_id": 1
}
```

---

### 5️⃣ 管理后台功能权限导入 / 导出

```http
POST /api/v1/admin/feature-permissions/export
POST /api/v1/admin/feature-permissions/import
```

设计约束：

1. 导出必须以当前勾选的权限为准，确保“明确选中了什么就导出什么”
2. 导出文件只保留权限元数据，不携带数据库主键
3. 导出文件必须带出权限所属应用，并按应用分组
4. 导入按 `permission_key` 幂等写入
5. 已存在权限做更新，不存在权限做创建
6. 导入时如果文件中的应用不存在，应先自动创建应用，再写入权限
7. 默认不删除目标服务器额外权限，避免把局部筛选导入误当成全量覆盖
8. 后台允许批量删除权限元数据，但不自动修改历史卡密中的旧权限 JSON
9. 应用管理页应成为权限管理与卡密管理的导航入口，而不是单纯静态展示页

导出文件结构示例：

```json
{
  "schema_version": "feature_permissions.v2",
  "exported_at": "2026-04-13T12:00:00",
  "total": 2,
  "filters": {
    "page": 1,
    "size": 20,
    "app_id": 1,
    "status": "normal",
    "keyword": "wechat"
  },
  "permissions": [
    {
      "permission_key": "wechat",
      "permission_name": "微信抓取",
      "app": {
        "app_id": 1,
        "app_key": "wechat_app",
        "app_name": "微信应用"
      },
      "description": "微信相关抓取能力",
      "category": "微信应用",
      "icon": "ChatDotRound",
      "sort_order": 1,
      "status": "normal"
    }
  ],
  "app_groups": [
    {
      "app": {
        "app_id": 1,
        "app_key": "wechat_app",
        "app_name": "微信应用"
      },
      "total": 1,
      "permissions": [
        {
          "permission_key": "wechat",
          "permission_name": "微信抓取",
          "app": {
            "app_id": 1,
            "app_key": "wechat_app",
            "app_name": "微信应用"
          },
          "description": "微信相关抓取能力",
          "category": "微信应用",
          "icon": "ChatDotRound",
          "sort_order": 1,
          "status": "normal"
        }
      ]
    }
  ]
}
```

导入流程：

```text
管理员上传导出文件
  ↓
服务端解析 JSON
  ↓
校验 schema_version 与 permissions 结构
  ↓
按 permission_key 执行创建 / 更新
  ↓
若应用不存在则先自动创建应用
  ↓
提交事务
  ↓
页面刷新展示最新权限列表
```

权限裁决优先使用当前卡密维度：当请求携带 `card_id` 时，只校验当前用户是否绑定该卡密、当前设备是否绑定该卡密、该卡密是否包含目标权限。只有未携带 `card_id` 时，才按用户和设备查询可用卡密作为兼容兜底，避免同一设备绑定多张卡密后权限被错误合并。

卡密权限配置约束补充：

- 卡密只能选择“当前卡密所属应用”的权限；
- 为兼容历史数据，系统允许同时读取 `app_id IS NULL` 的旧权限作为过渡；
- 老权限应通过升级脚本逐步补齐 `app_id`，而不是长期依赖兼容逻辑。

## 五、卡密生成接口（补全）

> **仅限后台 / 管理员使用**

### 1️⃣ 接口定义

```http
POST /api/admin/card/generate
Authorization: Bearer admin_token
```

请求参数：

```json
{
  "app_id": 1,
  "count": 100,
  "expire_time": "2026-01-01",
  "max_device_count": 2,
  "permissions": ["wechat", "ximalaya"],
  "remark": "高级套餐"
}
```

返回：

```json
{
  "cards": [
    "ABCD-EFGH-IJKL",
    "MNOP-QRST-UVWX"
  ]
}
```

---

### 2️⃣ 卡密生成规则（推荐）

* 长度：16～20 位
* 分段：4-4-4-4
* 字符集：`A-Z + 2-9`（避免 0/O/1/I 混淆）
* 唯一索引，防止重复

示例：

```
X9KD-A7QM-LP2E-W8RZ
```

---

### 3️⃣ 卡密初始状态

```text
status = unused
bind_user = null
bind_device = 0
```

首次绑定后：

```text
status = used
```

## 六、客户端强制策略

必须遵守：

1. 未登录 → 不进入主界面
2. 未绑定卡密 → 所有功能跳转到卡密绑定页
3. 每个功能执行前 → 调用权限校验接口

补充规则：

- 普通用户遵循上述卡密绑定约束
- 管理员属于系统级身份，不受卡密绑定与设备绑定限制，可直接访问后台和受权限保护的接口

即使被反编译，也无法绕过服务端。
